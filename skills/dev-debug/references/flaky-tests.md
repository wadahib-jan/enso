# 不安定テスト（flaky test）の診断と安定化

実行するたびに成否が変わるテストを扱うためのリファレンス。dev-debug のカテゴリ判定で「不安定テスト」に分類された場合に参照する。

## 原因の6分類

| 分類 | 典型的な症状 | 見るべき箇所 |
|---|---|---|
| **タイミング依存** | 実行が速い環境／遅い環境で結果が変わる | `await` 不足、`setTimeout` への依存、競合状態 |
| **共有状態** | 単体で実行すると通るが全体実行で落ちる | グローバル変数、DB の状態、ファイルシステムのテスト間汚染 |
| **外部サービス依存** | ネットワーク状況で結果が変わる | 実際の API 呼び出し、外部 DB への接続 |
| **ランダム性** | 一定の確率で落ちる | `Math.random`、`Date.now`、UUID 生成などの非決定的処理 |
| **順序依存** | 実行順序を変えると落ちる | 前のテストが作った状態への暗黙の依存 |
| **リソース制限** | 並列実行時や CI でだけ落ちる | メモリ不足、ファイルディスクリプタ枯渇、ポート競合 |

原因の切り分けは Explore サブエージェント（thoroughness: medium）に委ね、対象テストファイルとテスト対象の実装だけを読ませる。

## 分類ごとの修正方針

### タイミング依存

- 不足している `await` を追加する
- `setTimeout` による待機を、条件が満たされるまで待つ形（`waitFor` / `waitForExpect` 等）に置き換える
- テスト用のタイムアウト値を十分に確保する

### 共有状態

- `beforeEach` / `afterEach` で状態の初期化とクリーンアップを行う
- テストごとにユニークな ID・名前でデータを作る
- テスト間の依存関係そのものを排除する

### 外部サービス依存

- モック／スタブを導入して実際の呼び出しを避ける
- HTTP は MSW（Mock Service Worker）等でモックする
- DB はテスト用のインメモリ実装に切り替える

### ランダム性

- `Math.random` を seed 付き乱数生成に置き換える
- `Date.now` は `jest.useFakeTimers()` / `vi.useFakeTimers()` で固定する
- 非決定的な値はテスト用の固定値でモックする

### 順序依存

- 各テストが単独で成立するようにする
- 暗黙の前提条件を明示的な setup に変換する

### リソース制限

- `afterEach` でリソースを解放する
- 接続プールを適切に管理する

## 安定性の確認

修正後は同じテストを**最低3回連続**で実行し、全回成功して初めて安定化できたとみなす。1回でも落ちた場合は、前回と異なるアプローチで原因分析からやり直す。

安定化できなかった場合は、試したアプローチと、手動での対応が必要と判断した理由を報告に残す。

## ルール

- **テストの削除やスキップを「安定化」と呼ばない。** 検証されない状態になるだけである
- **assertion を弱めて通す修正をしない。** テストが何を検証しているかを変えてはならない
- 修正はテストコード側を優先し、実装コードの変更は最小限にとどめる
- 各リトライでは前回と異なるアプローチを試す

## 報告に残す項目

- 原因分類（上記6分類のどれか）と、そう判断した根拠
- 修正したファイルと変更内容
- 安定性確認の実行回数と結果
- 安定化できなかった場合は、試行内容と推奨する手動対応
