# Issue 本文テンプレート

`enso-issue-report` の Step 5 で使う。種別に対応するテンプレートを選び、ヒアリング結果で埋める。

**共通ルール**

- 埋められなかった項目は削除せず「不明」「取得できず」と書く。空欄のまま残すと、読み手が「聞き忘れ」なのか「該当なし」なのか判断できない
- 「該当箇所」は具体的なファイルパスまで絞れると、`enso-issue-fix` と `dev-plan` が探索を省いてそこから調査を始められる。絞れないときは無理に書かず「不明」とする
- 絶対パスのユーザー名は `~` に、業務プロジェクト名は `<project>` に置き換える

---

## bug テンプレート

```markdown
## 症状

<何が起きたか。1〜3文>

## 期待した動作

<どうなるはずだったか>

## 実際の動作

<代わりに何が起きたか>

## 再現手順

1. <どのプロジェクトで、どのスキルを、どう起動したか>
2. <次の操作>
3. <症状が出る>

**再現性**: 常に発生 / 特定条件で発生 / 一度だけ発生 / まだ再現していない

## エラーメッセージ

<原文のまま。無ければ「なし」。トークン・絶対パス中のユーザー名は伏せる>

## 該当箇所

<例: `skills/dev-plan/SKILL.md` の Phase 0.7 / `hooks/guard-bash.mjs` / 不明>

## 影響度

作業がブロックされる / 回避策はあるが手間 / 軽微

<回避策があれば書く>

## 環境

| 項目 | 値 |
|---|---|
| enso version | <plugin.json の version> |
| enso commit | <取得できたときのみ。無ければ「取得できず」> |
| Claude Code | <claude --version の出力> |
| OS | <uname -srm の出力> |
| 強制モード | 有効 / 無効 / 不明 |
```

## enhancement テンプレート

```markdown
## 解決したい課題

<今どう困っているか。「〜がしたいが、〜のためできない」の形で書く>

## 提案する挙動

<どう変わってほしいか。具体的に>

## 現状の回避策

<今どうしのいでいるか。無ければ「なし」>

## 影響範囲

<変更が及びそうなスキル・hooks・ドキュメント。分かる範囲で>

## 該当箇所

<例: `skills/dev-plan/SKILL.md` の Phase 5e / 新規スキル / 不明>

## 補足

<代替案、参考にした他ツールの挙動など。無ければ削除>

## 環境

| 項目 | 値 |
|---|---|
| enso version | <plugin.json の version> |
| Claude Code | <claude --version の出力> |
```

## documentation テンプレート

```markdown
## 対象ドキュメント

<例: `MANUAL.md` の「### 4. dev-plan」/ `README.md` の強制モードの節>

## 現在の記述

> <該当箇所の引用>

## 問題

<何が誤っている / 不足している / 実装と食い違っているか>

## あるべき記述

<こう書かれているべき、という案。案が無ければ「要検討」>

## 根拠

<実装のどこを見てそう判断したか。例: `hooks/guard-bash.mjs` は ready のみを見ている>

## 環境

| 項目 | 値 |
|---|---|
| enso version | <plugin.json の version> |
```
