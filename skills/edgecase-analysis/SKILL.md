# Edgecase Analysis（エッジケース・異常系分析）

6つのレイヤーと4つの複合カテゴリを並列に分析し、見落としがちな異常系シナリオを洗い出して P0〜P3 の優先度付きチェックリストにまとめる。

## 前提知識

### 使いどころ

設計が固まった直後、実装に入る前。異常系の考慮漏れは実装後に見つかると手戻りが大きい。

```
dev-plan（設計・受入基準）
        ↓
  edgecase-analysis  ← ここ
        ↓ check_list.md（P0〜P3）
   dev-plan の受入基準へ反映 / dev-webtest-plan のテスト計画へ反映
```

### 他スキルとの違い

**ゼロから異常系を洗い出せるのは本スキルだけ。**

- **rev-docs** — requirements フェーズが既存のバリデーション実装からエッジケース「要件」を抽出する。実装済みのものしか拾えない
- **uat-test-design** — 既存の仕様書やテストに書かれている異常系を機械的に名寄せする。書かれていないものは拾わない
- **dev-webtest-plan** — 受入基準からE2Eシナリオを作る。エッジケース抽出の専用フェーズを持たない

### 2つの分析モード

| モード | 起動条件 | 入力 |
|---|---|---|
| requirements-based | 要件定義書が存在する | 要件定義書・設計文書・タスクノート |
| source-based | 要件定義書が無い | ソースコードから収集した情報 |

## ワークフロー

### Step 0: 分析モードの判定

引数が無い場合は「引数に要件名または分析対象を指定してください（例: `/enso:edgecase-analysis ユーザー認証システム`）」と伝えて終了する。

要件定義書の存在を確認する。以下の順に探す。

1. `docs/dev/plans/{$1}/requirements.md`（dev-plan Full-spec の出力）
2. `docs/spec/{$1}/requirements.md`（rev-docs の出力）

**存在する場合**: `分析モード = "requirements-based"`、`要件名 = $1` として「要件定義書「{{要件名}}」に基づいてエッジケース分析を実施します」と宣言し、Step 1 へ。

**存在しない場合**: AskUserQuestion で分析方法を確認する（質問「要件定義書が見つかりません。どのように分析を進めますか?」/ header「分析方法」）。

- **ソースコードから分析（推奨）** → `分析モード = "source-based"`、`分析対象 = $1` として Step 1-source へ
- **要件定義書を作成してから分析** → 「先に `/enso:dev-plan {要件名} "{要件概要}"` を Full-spec モードで実行してください」と案内して終了

### Step 1: 要件情報の収集（requirements-based）

以下を Read して収集情報にまとめる。

- 要件定義書（上記で見つかったパス）
- 設計文書 — `docs/dev/plans/{要件名}/` 配下、または `docs/spec/{要件名}/design.md`、`docs/design/` の関連文書
- 受入基準 — `docs/dev/plans/{要件名}/acceptance-criteria.md`（あれば）
- タスクノート — `docs/spec/{要件名}/note.md`（あれば）
- 既存のエッジケース分析 — `docs/dev/analysis/*_edgecase/` を検索し、あれば最新を参照

収集情報として保持する: 要件の概要 / 主要機能リスト / 既知の制約事項 / 技術スタック / 各文書の内容。Step 2 へ。

### Step 1-source: ソースコードからの情報収集（source-based）

「ソースコードから「{{分析対象}}」に関連するエッジケースを分析します」と宣言する。

Task ツール（`subagent_type: "Explore"`, `model: "haiku"`）で以下を収集する。

1. **関連ソースコードの特定** — メインロジック（ビジネスロジック、コントローラー、サービス等）、データモデル・スキーマ定義、API エンドポイント定義、UI コンポーネント、テストコード、設定ファイル
2. **技術スタックの把握** — フレームワーク、ライブラリ、データベース・ストレージ、外部API・サービス連携
3. **アーキテクチャパターンの理解** — レイヤー構造、データフロー、エラーハンドリング方針、非同期処理の有無、認証・認可の仕組み
4. **既存のエラーハンドリング状況** — try-catch の使用箇所、バリデーションの実装、リトライ・フォールバック処理、ログ出力

収集結果のサマリー（主要ファイル、技術スタック、識別されたリスク領域）をユーザーに提示し、**続行確認を得てから** Step 2 へ。

### Step 2: 分析スコープの決定

AskUserQuestion でスコープを確認する（header「分析スコープ」）。

- **包括的分析（推奨）** — 全レイヤーを網羅的に分析。発生可能性・影響度を詳細評価
- **重点分析** — 主要レイヤーのみ。Must Have 要件に集中
- **カスタム** — 対象レイヤーを個別に選択

カスタムの場合は続けて対象レイヤーを確認する（header「対象レイヤー」/ `multiSelect: true`）: アプリケーション層 / UI層 / データ管理層 / ネットワーク通信層 / 非同期処理層 / 認証・認可層 / 複合的エッジケース。

### Step 3: 初期分析とチェックリスト初期化

```bash
PROJECT_ROOT="$(git rev-parse --show-toplevel)"
TIMESTAMP="$(date +%Y%m%d%H%M%S)"
BASE_DIR="$PROJECT_ROOT/docs/dev/analysis/${TIMESTAMP}_{{英語化名}}_edgecase"
mkdir -p "$BASE_DIR"
```

`check_list.md` を以下の内容で初期化する。

```markdown
# エッジケース分析チェックリスト

**分析対象**: {{分析対象名}}
**分析モード**: {{分析モード}}
**実施日時**: {{実施日時}}

---

## P0: 即座に対応が必要

## P1: 早急に対応

## P2: 計画的に対応

## P3: 監視

---

*このチェックリストは分析の進行に伴い自動更新されます*
```

ユーザーが既存のチェックリストを指定している場合は Read して「既存チェックリスト」に取り込む（形式: `- [ ] P0 説明 [リンク](path)`）。重複追加を防ぐために使う。

`references/initial-analysis-template.md` を Read し、context で埋めて Task ツールで実行する（`subagent_type: "general-purpose"`, `model: "opus"`）。出力先は `initial_analysis.md`。

### Step 4: レイヤー別分析（6並列）

初期分析結果を Read で確認し、「6つのレイヤー（アプリケーション、UI、データ管理、ネットワーク、非同期、認証）を並列分析します」と報告して続行確認を得る。

`references/layer-analysis-template.md` を Read する。**1つのメッセージで6つの Task を並列実行**し、各 Task には同じテンプレートを渡したうえで担当レイヤーを指定する（`subagent_type: "general-purpose"`, `model: "opus"`）。

| 担当レイヤー | 出力ファイル |
|---|---|
| アプリケーション層 | `layer_analysis_app.md` |
| UI層 | `layer_analysis_ui.md` |
| データ管理層 | `layer_analysis_data.md` |
| ネットワーク通信層 | `layer_analysis_network.md` |
| 非同期処理層 | `layer_analysis_async.md` |
| 認証・認可層 | `layer_analysis_auth.md` |

全ファイルの作成を Read で確認したあと、各結果からチェックリスト項目を抽出し、**既存項目と重複しないものだけ** `check_list.md` に Edit で追記する（形式: `- [ ] P0 説明 [ファイル名](./layer_analysis_*.md#anchor)`）。

最後に Task で `layer_analysis_summary.md` を生成し、全レイヤーの統計を集約する。

### Step 5: 複合エッジケース分析（4並列）

`layer_analysis_*.md` をすべて Read し、「4つのカテゴリ（データモデル状態、複数レイヤー、カスケード障害、タイミング依存）を並列分析します」と報告して続行確認を得る。

`references/combined-analysis-template.md` を Read する。**1つのメッセージで4つの Task を並列実行**し、各 Task に担当カテゴリを指定する。

| 担当カテゴリ | 出力ファイル |
|---|---|
| データモデル状態の組み合わせ | `combined_analysis_data_state.md` |
| 複数レイヤーにまたがるケース | `combined_analysis_multi_layer.md` |
| カスケード障害 | `combined_analysis_cascade.md` |
| タイミング依存の問題 | `combined_analysis_timing.md` |

Step 4 と同様にチェックリストを重複排除して更新し、`combined_analysis_summary.md` を生成する。

### Step 6: 最終レポートと完了報告

すべての分析結果を Read したうえで、`references/final-report-template.md` を使い Task で `final_report.md` を作成する（**500行以内**、全分析結果と `check_list.md` へのリンクを含める）。

`index.md` を Edit で更新し、全ファイルへのリンク・チェックリストへのリンク・サマリーを載せる（枝番ファイルがある場合はそれも）。

`check_list.md` を Read して P0/P1/P2/P3 の項目数をカウントし、重複がないことを確認する。

完了報告に含める内容:

- 発見されたエッジケースの総数
- レイヤー別の内訳
- 複合エッジケースの内訳
- 高リスク（影響度:高 かつ 発生可能性:中以上）のケース数
- チェックリスト項目数（P0/P1/P2/P3 別）
- 推奨される対応優先順位
- 出力されたファイル数
- **`check_list.md` のパスを強調表示する**（これが最も使われる成果物）

## 分析対象カテゴリ

| レイヤー | 主な観点 |
|---|---|
| アプリケーション層 | ビジネスロジックの状態遷移、バリデーションルール、並行実行 |
| UI層 | 画面状態、ユーザー操作の組み合わせ、入力値 |
| データ管理層 | トランザクション、データ整合性、キャッシュ、データ同期 |
| ネットワーク通信層 | HTTPステータスコード、タイムアウト、リトライ |
| 非同期処理層 | ジョブキュー、ワークフロー、並行処理 |
| 認証・認可層 | セッション、権限、トークン |

複合カテゴリ: データモデル状態の組み合わせ / 複数レイヤーにまたがるケース / カスケード障害 / タイミング依存の問題

## 優先度の基準

| 優先度 | 基準 |
|---|---|
| P0 | 即座に対応が必要。データ破損・セキュリティ侵害・サービス停止につながる |
| P1 | 早急に対応。主要機能が使えなくなる、または誤った結果を返す |
| P2 | 計画的に対応。限定的な条件下でのみ発生し、回避策がある |
| P3 | 監視。理論上は起こりうるが、発生可能性が極めて低い |

## 信号機システム

各エッジケースに確信度を付与する。

- 🔵 **前工程指示** — 要件・設計に明記されている、またはコード上で未処理を確認できた
- 🟡 **妥当な推測** — 一般的なパターンから導いたが、この実装で起こるかは未確認
- 🔴 **AI推論補完** — 実行環境・外部システム・タイミングに依存し、静的には確認できない

**🔴 のケースこそ本スキルの価値。** 見落とされやすいので、確度が低くても切り捨てず「要検証」として残す。ただし P0/P1 に分類するには 🔵🟡 の裏付けを求める。

## ルール・制約

- 分析結果内のファイルパスは**プロジェクトルートからの相対パス**で統一する。絶対パスは記載しない
- Bash コマンドはプロジェクトルートの **絶対パス** を使う。worktree セッション中はコマンド置換（`$(...)`）で組み立てず、確定済みの絶対パスを直接書く
- 各分析ファイルは500行以内。超える場合は枝番（`_1.md`, `_2.md`）に分割する
- 最終レポートは500行以内
- **Step 4 と Step 5 は必ず並列実行する**（1メッセージで6つ／4つの Task）。直列にすると分析時間が数倍になる
- チェックリストへの追記は必ず重複チェックを行う
- Step 1-source と Step 4・Step 5 の前にユーザーの続行確認を得る
- サブエージェントの結果は要約のみメインコンテキストに返す
