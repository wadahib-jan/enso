# Feature Rubber Duck（アイデア整理とPRD作成）

まだ形になっていないアイデアを、対話を繰り返しながら実装可能な PRD（Product Requirements Document）まで落とし込む。

## 前提知識

### 使いどころ

**要件がまだ言語化できていない段階。** 何を作るか決まっていれば dev-plan に直行してよい。

```
[「なんとなくこういうのが欲しい」]
        ↓
 feature-rubber-duck  ← ここ（対話で具体化）
        ↓ prd.md
 /enso:dev-plan <name> <prd.md のパス>
        ↓
   計画 + Draft PR
```

**dev-plan は PRD ファイルパスを引数に取れる。** この受け渡しが本スキルの設計上の位置づけ。

### 他スキルとの違い

- **dev-plan（Full-spec）** — 要件が言語化できている前提で、EARS 要件定義・ユーザーストーリー・受入基準を作る。「何を作るか」が固まっていないと機能しない

## ワークフロー

### Step 1: 初期ヒアリング

引数がある場合は初期アイデアとして記録する。無い場合は「どのような機能やアイデアについて相談したいですか？」と尋ねる。

AskUserQuestion で以下を確認する。

| # | 質問 | header | 選択肢 |
|---|------|--------|--------|
| 1 | このアイデアはどのカテゴリに該当しますか？ | カテゴリ | 新機能の追加 / 既存機能の改善 / 技術的な改善 / バグ修正・問題解決 |
| 2 | この機能の優先度はどの程度ですか？ | 優先度 | 高（すぐに必要）/ 中（近い将来必要）/ 低（あると良い）/ 調査中（まだ決まっていない） |
| 3 | 関連する技術やコードベースをどの程度理解していますか？ | 理解度 | 詳しく理解している / ある程度理解している / あまり理解していない / 全く理解していない |

context として保持する: アイデアの概要 / カテゴリ / 優先度 / 理解度 / 関連する既存機能 / 技術的制約。収集内容をユーザーに宣言する。

### Step 2: セッション初期化

```bash
PROJECT_ROOT="$(git rev-parse --show-toplevel)"
BASE_DIR="$PROJECT_ROOT/docs/dev/analysis/{{timestamp}}_{{アイデアの英語化}}"
mkdir -p "$BASE_DIR"
```

- `timestamp` は `yyyyMMddHHmmss` 形式
- `アイデアの英語化` はスネークケース・最大30文字程度。例: `注文履歴のエクスポート機能` → `order_export`、`決済方法の追加` → `payment_integration`、`CSVインポート` → `csv_import`

セッションファイルを準備する。

| ファイル | 内容 |
|---|---|
| `index.md` | セッション全体のインデックス |
| `conversation.md` | 会話履歴の記録 |
| `context.md` | 整理されたコンテキスト情報 |
| `research.md` | 技術調査・コード調査の結果 |
| `prd.md` | 最終的な PRD |

`index.md` を作成してセッション情報を記録し、Step 3 へ。

### Step 3: 対話イテレーション

イテレーション回数を +1 して、以下を1サイクルとして回す。

1. **現状の理解を整理して提示** — これまでの整理内容を簡潔にまとめる
2. **不明点や確認事項を質問** — リストアップしてユーザーに投げる
3. **必要な調査を実施**
   - コードベース調査 → Task ツールで関連コードを検索・分析
   - 技術調査 → WebSearch / WebFetch で技術情報を収集
   - 既存機能確認 → Read / Grep で既存実装を確認
4. **新しい情報を context に統合**
5. **ファイルを更新** — `conversation.md` と `context.md`。調査した場合は `research.md` も
6. **次のアクションを判断**（下記ルール）

**最大10イテレーション。** 達したら現状をまとめて PRD 作成を提案する。

### Step 4: PRD作成

`references/prd-template.md` を Read し、context で埋めて Task ツールで `{{ベースディレクトリ}}/prd.md` を作成する（`subagent_type: "general-purpose"`）。

`index.md` を最終更新し、全セッションファイルのパスを整理して表示する。

**完了時に次の一手を明示する。**

```
PRD を作成しました: docs/dev/analysis/<dir>/prd.md

実装計画に進む場合:
  /enso:dev-plan <plan-name> docs/dev/analysis/<dir>/prd.md
```

## 判断ルール

### Step 3 を継続する条件（いずれかに該当）

- アイデアがまだ曖昧で具体化が必要
- 追加の技術調査や検証が必要
- 既存コードベースとの統合方法が不明確
- ユーザーからの追加情報待ち
- イテレーション回数が最大未満

### Step 4 に進む条件（すべてに該当）

- アイデアが十分に具体化されている
- 技術的な実現可能性が確認されている
- 要件が明確に定義されている
- **ユーザーが PRD 作成に合意している**

### セッション終了条件

- イテレーション回数が10に達した
- ユーザーが明示的に終了を希望した

## 対話のガイドライン

### 質問の仕方

- オープンエンドな質問から始める
- 具体的な選択肢を提示して絞り込む
- 技術的な詳細は段階的に深掘りする
- **ユーザーの理解度に合わせた説明をする**（Step 1 の質問3で把握済み）

### 整理の方法

- 5W1H（Who, What, When, Where, Why, How）を意識する
- ユーザーストーリー形式で要件を整理する
- 技術的な実現方法と要件を分けて考える
- 優先順位をつけて整理する

### 調査のタイミング

- コードベースの既存機能を確認する必要がある時
- 技術的な実現可能性を検証する必要がある時
- 類似機能の実装例を探す時
- 外部ライブラリや API の情報が必要な時

### Task 利用のガイドライン

- 複雑なコードベース調査は Task で実施する
- 会話が長くなりコンテキストが複雑になってきたら Task を使う
- **調査結果は必ずファイルに保存する**（後続のイテレーションで参照するため）

## 信号機システム

PRD の各要件に確信度を付与する。

- 🔵 **前工程指示** — ユーザーが明示的に述べた要件
- 🟡 **妥当な推測** — 対話の流れから補完した要件。ユーザーの確認は取れている
- 🔴 **AI推論補完** — 未確定のまま PRD に含めた要件。判断を保留した箇所

**🔴 は PRD の「未確定事項」セクションにまとめる。** dev-plan がこれを引き継いで解消できるようにするため、曖昧なまま断定的に書かない。

## ルール・制約

- PRD 内のファイルパスは**プロジェクトルートからの相対パス**で統一する。絶対パスは記載しない
- Bash コマンドはプロジェクトルートの **絶対パス** を使う。worktree セッション中はコマンド置換（`$(...)`）で組み立てず、確定済みの絶対パスを直接書く
- 各セッションファイルは500行以内を目標とする
- **ユーザーの合意なく PRD 作成に進まない。** 対話の打ち切りはユーザーが決める
- 会話履歴は毎イテレーション記録する（セッションを中断・再開できるようにするため）
- 実装は行わない。PRD の作成までが担当範囲

## 追加リソース

- **`references/prd-template.md`** — PRD 作成用のプロンプトテンプレート。PRD の全セクション構成を含む
