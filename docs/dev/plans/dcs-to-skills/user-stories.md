# User Stories: dcs-to-skills

## ペルソナ

**P1: Enso 利用者** — 自分のプロジェクトで Enso を使って開発する人。コマンド一覧から「今の状況に合うもの」を選びたい。DCS という内部呼称には関心がない。

**P2: Enso 開発者** — Enso 本体をメンテナンスする人。重複した機能を抱え続けたくない。

## エピック1: 使うべきスキルが判別できる

- **US-101** (Must): P1 として、スキル一覧を**開発フェーズ別**に見たい。なぜなら、10本がフラットに並んでいても自分の状況に合うものを選べないから。
- **US-102** (Must): P1 として、役割が近いスキルの**使い分け**を知りたい。なぜなら、`bug-analysis` と `dev-debug` のどちらを使うべきか毎回迷うから。
- **US-103** (Should): P1 として、`/enso:help` や `dev-navigate` からも同じ基準で案内されたい。なぜなら、入口によって推奨が食い違うと混乱するから。

## エピック2: 重複した機能に悩まされない

- **US-201** (Must): P1 として、既存スキルで代替できる機能は一覧から消えていてほしい。なぜなら、選択肢が多いほど選べなくなるから。
- **US-202** (Must): P2 として、削除したコマンドへの参照が残っていない状態にしたい。なぜなら、壊れたリンクが利用者を迷わせるから。

## エピック3: 分析から次の工程へつながる

- **US-301** (Must): P1 として、`feature-rubber-duck` の PRD をそのまま `dev-plan` に渡したい。なぜなら、整理した内容を手で書き直したくないから。
- **US-302** (Must): P1 として、`bug-analysis` で原因が分かったらそのまま修正に進みたい。なぜなら、原因調査と修正が分断されていると二度手間になるから。
- **US-303** (Should): P1 として、`edgecase-analysis` のチェックリストを受入基準やテスト計画に反映したい。

## エピック4: 汎用フレームワークとして使える

- **US-401** (Must): P1 として、スキル定義に他人のプロジェクト固有の名前やパスが混ざっていない状態で使いたい。なぜなら、自分のプロジェクトと無関係な前提で分析されると精度が落ちるから。

## ジャーニー

```
アイデアがある
  → feature-rubber-duck（PRD化）
  → dev-plan <name> <prd.md>（計画 + Draft PR）
  → edgecase-analysis（異常系の洗い出し）→ 受入基準へ反映
  → impact-analysis（既存への波及確認）
  → dev-loop（実装〜検証）

バグ報告が来た
  → bug-analysis（原因特定）
  → dev-debug（修正と検証）

本番が遅い
  → performance-analysis（原因調査）
  → dev-impl（改善実装）

既存コードが分からない
  → sequence-diagram-analysis / state-transition-analysis（可視化）
```
