## 個別の確認事項

### 正規表現による ReDoS

`findLoopStates()` は `new RegExp(\`^${field}:\\s*(.+?)\\s*$\`, "m")` を組み立てる。`field` は**モジュール内の固定配列 `LOOP_STATE_FIELDS` の要素のみ**で、外部入力が混入する経路が無い。本差分で追加した2要素（`impl_approved_at` / `merge_approved_at`）も正規表現メタ文字を含まない。

`mergeTarget()` の `/^(?:.*\/pull\/)?(\d+)$/` はバックトラックの分岐を持たず、入力はコマンド文字列1トークン。ReDoS の懸念なし。

### プロトタイプ汚染

`loop-state.yaml` から読んだ値を `state[field]` に代入するが、`field` は固定ホワイトリスト。`__proto__` 等のキーが混入する経路が無い。

### 日時パース

`approvalStatus()` は `Date.parse()` の結果を `Number.isNaN` で検査し、解釈できない値を `"invalid"`（＝ deny 側）に倒す。**解析失敗が「通す」側に倒れない**ことを確認した。

### 判定の失敗モード

新ガードの分岐はいずれも「判定できないときに緩む」方向へ倒れないことを確認した。

| 状況 | 挙動 |
|---|---|
| `loop-state.yaml` を読めない | 記録なし扱い → `deny` |
| 日時が壊れている | `invalid` → `deny` |
| 記録が古い | `stale` → `deny` |
| 対応する計画が見つからない | `ask`（意図的な緩和。Info-2 参照） |

## Info（設計上の受容事項）

### Info-1: 承認記録はリポジトリ内のファイルであり、書き換えを防げない

`merge_approved_at` は `loop-state.yaml`（リポジトリ内の平文ファイル）に置かれる。**リポジトリに書き込める者は記録を偽造できる**ため、これは悪意ある人間に対する権限制御ではない。

本ガードの目的は Issue #24 のとおり「**モデルが承認ゲートを飛ばしたことをツール段階で検出する**」ことにあり、脅威モデルは人間の攻撃者ではない。記録の偽造は「ゲートを飛ばしたうえで記録だけ先に書く」という明示的な逸脱であり、`dev-cleanup` のルールに「先回りして書かない」を明記して抑止する（`skills/dev-cleanup/SKILL.md`）。また記録はコミット・push されるため、**偽造は git 履歴に残る**（監査可能）。

- IPA 出典: 安全なウェブサイトの作り方 改訂第7版 / 1.11 アクセス制御や認可制御の欠落 / p.63-66 / https://www.ipa.go.jp/security/vuln/websecurity/about.html
- 判定: **受容**。暗号署名等でこれを防ぐことは Issue のスコープ外であり、費用対効果も見合わない

### Info-2: 対応する計画が無い PR は `ask` に緩和される

`gh pr merge` の対象に紐づく `loop-state.yaml` が見つからない場合、`deny` ではなく `ask`（利用者への確認）に落とす。enso の計画を経ない正当な手動マージ（他者の PR、hotfix 等）を締め出さないための意図的な緩和である。

このため「`loop-state.yaml` を削除してからマージする」経路では確認プロンプトまでしか落ちない。ただしこれも人間の明示的操作を要し、Info-1 と同じ脅威モデルの外にある。

- IPA 出典: 安全なウェブサイトの運用管理に向けての20ヶ条 / 第4条 運用ルールの明文化 / https://www.ipa.go.jp/security/vuln/websecurity/about.html
- 判定: **受容**。プロンプトに落ちる時点で人間の目に触れる
